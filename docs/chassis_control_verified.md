# 底盘控制实测规范（v2，已验证）

> 本文取代 `chassis_wiring_and_control_spec.md` 中关于引脚映射与信号行为的部分。
> 所有结论均在实车（VENTUNO Q + 该底盘）上实测确认，日期 2026-10-29。

---

## 1. 结论速览

| 项目 | 结论 |
|---|---|
| 信号 | 50 Hz，1000–2000 µs 正脉冲，3.3 V 高有效 |
| 3 号 | **速度大小**（不是方向）：1500 停，>1500 给速度（1% ≈ 5 µs），<1500 是**刹车** |
| 4 号 | 转向：1500 居中，**+ = 右**、− = 左，±400 µs 满舵 |
| 5 号 | **方向**：1000 = 前进，1500 = 倒车（实测 2026-10-31，与旧文档相反）**必须配合油门** |
| 1/2/6 号 | **当前未接线**（D9/D10/D11 悬空）。实测：缺这三路**不会**阻止运动，所以「缺通道会进失效保护」这个假设是**错的**，不能当安全依赖 |
| 板子前提 | **SW2 拨码第 8 位必须打开**，否则外部 PWM 完全无效 |
| 接收机 | 串阻 R89/R90/R91 已拆除，遥控失效 |

## 2. 接线表

| 小车「接收机测试点」 | VENTUNO Q | 说明 |
|---|---|---|
| `1` | `D9` | 保持中位 |
| `2` | `D10` | 保持中位 |
| `3` | `D3` | 油门 |

## 3. 平台侧坑（与本项目强相关）

1. **Arduino core 不能用 0.90.0**
   `arduino:zephyr 0.90.0` 里 VENTUNO Q 的板定义是照 UNO Q（STM32U585）抄的，
   烧进去的 loader 会在这颗 STM32H5F5 上启动即 bus fault（`K_ERR_ARM_BUS_PRECISE_DATA_BUS`），
   MCU 停在 `arch_system_halt`，程序永远不跑。

   > 2026-10-31 更新：当时写的「必须是 1.0.0」已过时。当前安装 **1.1.0**，
   > loader 版本 `v4.4.2-188-ga12e8f37553a`，底盘固件 / 中位固件 / rc_min 均正常加载运行。

2. **烧录后必须软件复位**
   这块板 OpenOCD 用 linuxgpiod 位操作 SWD，`stm32h5x.cfg` 复位时执行
   `adapter speed 480` 不被支持 → `reset` 失败 → MCU 被留在 DFU（USB `0483:df11`）。
   解决：烧完后用 `AIRCR.SYSRESETREQ`（`mww 0xE000ED0C 0x05FA0004`）复位。
   已封装为 `scripts/flash_chassis.sh`。

3. **不要与 App Lab 的部署流程混用**
   `arduino-app-cli app restart` 会重新编译烧录，同样卡在复位那一步；
   调试期统一用 `flash_chassis.sh`。

## 4. Linux 控制接口

MCU 通过 RouterBridge 暴露 RPC：

| 方法 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `drive` | `speed, steer`（-100..100） | `true` | 常规驾驶；`speed<0` 自动切倒档 |
| `set_pwm` | `thr_us, steer_us, gear_us` | `true` | 直接写脉宽，诊断用 |
| `stop` | — | `true` | 立即回中位 |
| `brake` | — | `true` | 轻刹（油门 1400） |
| `ping` | — | `"PONG"` | 心跳 |

### 4.1 安全语义

- **500 ms 看门狗**：超时无新指令 → 自动回中位（Linux 崩溃也不会失控）
- **斜率限制**：每帧最多变 1%（约 50%/秒），起步/停车平滑
- **死区**：|指令| < 3% 视为 0
- **上电默认**：六路全部 1500

### 4.2 Python 用法

```python
import sys
sys.path.insert(0, "scripts")
from car import Car

car = Car()            # 后台 20 Hz 持续下发
car.drive(30, 0)       # 油门 30% 直行
car.drive(30, 20)      # 边走边转（符号方向待标定）
car.drive(-25, 0)      # 倒车
car.stop()
car.close()
```

直接调 Bridge 也可以（必须持续调用，否则看门狗停车）：

```python
from arduino.app_utils import Bridge
Bridge.call("drive", 30, 0)
```

### 4.3 运行位置（权限）

`/var/run/arduino-router.sock` 属于 `root:arduino-router`。因此：

- **推荐**：把控制代码放在 App Lab 的 app 容器里运行（容器内可直接访问）
- 或者把用户加入该组（需重新登录）：

```bash
sudo usermod -aG arduino-router $USER
```

## 5. 烧录

```bash
./scripts/flash_chassis.sh                    # 底盘控制固件（chassis_v2_atomic，默认）
./scripts/flash_chassis.sh chassis_neutral    # 中位待机固件（安全态）
```

脚本做的事：编译 → **`reset halt`** → 用 OpenOCD 把 sketch 写入 `0x08100000`
→ 校验 → `SYSRESETREQ` 复位 → 等 MCU 的 USB（`1209:ca01`）重新枚举。

`reset halt` 和严格判定是 2026-10-31 加的：只 `halt` 时 flash 算法可能超时，
会写出半截镜像并静默报成功（表现为红灯 3 短闪）。
细节见 `docs/chassis_loader_red_led_incident.md`。

## 6. 排障清单（按顺序查）

1. **SW2 第 8 位**是否打开？（90% 的“完全没反应”都是这里）
2. 小车是否上电？蜂鸣器有节奏地响 = 板子活着且在收信号
3. 六路信号线是否都插好？`GND` 是否只有一根、接触良好？
4. `flash.sh` 是否报“已写入并启动”？MCU 是否还在 DFU（`lsusb | grep 0483`）？
5. core 版本是否正常（`arduino-cli core list`：1.1.0 已实测可用；0.90.0 会有 bus fault）
6. R89 是否短接（3 号通路）？

> **STM 区 LED1 红灯闪 3 下 + 停 1 s = sketch 没加载起来**（loader 报错），
> 跟接线、信号完全无关。先看 `lsusb | grep 1209`：不枚举就是镜像问题。
> 成因与处置见 `docs/chassis_loader_red_led_incident.md`。

## 8. 档位通道（D6 / 5 号）实测：**不是简单阈值**

2026-10-31 扫描，油门固定 D3=1650 µs（30%），D5=1500 居中，D6 各跑 5 秒：

| D6 脉宽 | 实测方向 |
|---|---|
| 1000 µs | 前进（多次验证） |
| 1250 µs | **先前进，随后突然切成倒车**（不稳定） |
| 1400 µs | 倒车 |
| 1500 µs | 倒车（多次验证） |
| 1600 µs | 倒车 |
| 2000 µs | **前进** |

结论：

1. **不是「>1500 一个方向、<1500 另一个方向」的阈值关系**，而是中间有一段「倒车窗口」：
   低端（≈1000）前进、中段（≈1300–1700）倒车、高端（2000）又回到前进。
2. **1250 落在窗口边缘，板子会在两个方向之间来回切** —— 这种值绝对不能用。
3. 因此固件只使用两个**已验证稳定**的值：
   `GEAR_FWD=1000`（前进）/ `GEAR_REV=1500`（倒车），不做任何中间值。
4. 安全含义：档位信号异常（浮空、越界）可能被解释成**前进**，
   所以「MCU 死了 = 车会停」这个假设不成立，必须保留物理急停。
   详见 `docs/chassis_estop.md`。
